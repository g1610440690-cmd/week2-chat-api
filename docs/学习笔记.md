## 1. 异步（async / await）：为什么 FastAPI 快

### 1.1 同步的问题

传统 Web 框架（如 Flask）每个请求占用一个线程。请求来了 → 线程去读数据库 → **阻塞等待** 数据库返回 → 期间这个线程啥也干不了。1000 个并发请求就要 1000 个线程，线程切换开销巨大，数据库连接也撑不住。

### 1.2 异步的核心：事件循环

Python 的 asyncio 用**单线程 + 事件循环**处理并发：

```
请求 A 来了 -> 发起数据库查询（不等待，立刻让出控制权）
请求 B 来了 -> 发起 Redis 查询（不等待，立刻让出控制权）
数据库返回 A 的结果 -> 事件循环唤醒 A 的协程继续执行
```

关键点：**等待 IO 时不占着 CPU**。`await` 就是"我现在要等 IO，先让别的协程跑"。

```python
# 同步写法：等待时整个线程卡住
result = db.query(...)          # 卡在这里等

# 异步写法：等待时让出控制权，事件循环去干别的
result = await db.execute(...)  # 挂起，等结果回来后继续
```

### 1.3 在本项目哪里看

- `app/database.py`：`create_async_engine`（异步引擎）
- 所有路由：`async def send_message(...)`，内部 `await db.commit()`、`await redis_manager.rate_limit(...)`
- `app/services/chat_service.py`：`stream_reply` 是**异步生成器**，`async for chunk in ...` 逐块消费

### 1.4 两个必背的坑

1. **不要在 async 函数里写阻塞代码**（如 `time.sleep`、同步 `requests.get`）。会卡住整个事件循环，所有请求一起变慢。要用 `await asyncio.sleep()`、`httpx.AsyncClient`。
2. **CPU 密集任务不适合 async**（如图像处理、复杂计算）。那种场景用多进程/线程池，或交给消息队列。

## 2. 连接池：为什么数据库要"池子"

### 2.1 问题

建立一条数据库连接 = TCP 握手 + 认证 + 分配内存，成本很高（毫秒级）。如果每个请求都新建、用完就断：
- 高并发下数据库被连接风暴打挂
- 每次请求多花几毫秒在"建连"上

### 2.2 连接池是什么

提前建好一批连接放在池里。请求来了**借**一条，用完**还**回去。池子管理：连接数量上限、排队等待、过期回收、失效剔除。

### 2.3 本项目参数对照（app/database.py）

```python
engine = create_async_engine(
    settings.DATABASE_URL,
    pool_size=5,        # 池中常驻最多 5 条连接
    max_overflow=10,    # 峰值时最多再临时开 10 条（上限共 15）
    pool_timeout=30,    # 池被借空时最多等 30 秒，超时抛异常
    pool_recycle=1800,  # 连接 30 分钟强制回收（防被数据库/防火墙静默断开）
    pool_pre_ping=True, # 借出前 ping 一下，坏连接自动剔除（数据库重启后能自愈）
)
```

### 2.4 排障：连接池相关症状

| 症状 | 原因 | 处理 |
|---|---|---|
| 日志报 `TimeoutError: Pool timeout` | 并发超过 pool_size+max_overflow，或连接泄漏 | 调大池子；检查是否忘了 `await db.close()`（用 `async with` 就不会漏） |
| 数据库重启后应用一直报错 | 池里全是死连接 | 开 `pool_pre_ping=True` |
| 连接数一直涨不降 | 长事务 / 连接泄漏 | 检查事务是否及时 commit/rollback |

## 3. 缓存与 Redis：临时状态放内存

### 3.1 为什么需要 Redis

数据库是"慢存储"（磁盘、要解析 SQL）。有些数据：
- **变化快**（限流计数：1 秒内自增几十次）
- **读多写少**（热门会话标题、配置）
- **临时性**（验证码、心跳、草稿）

这些写数据库很浪费，写内存（Redis）又快又省。所以架构惯例是：**持久化数据 → 数据库；临时状态 → Redis**。

### 3.2 本项目两个用途（app/redis_client.py）

**用途一：限流（固定窗口计数）**

```python
pipe = self._client.pipeline()
pipe.incr(f"rl:chat:{user.id}")   # 计数 +1（原子操作）
pipe.expire(key, 60)              # 60 秒窗口
```

每用户每分钟最多 `RATE_LIMIT_PER_MINUTE` 次聊天请求，超了返回 429。

**用途二：缓存（cache_get / cache_set）**

存短时效数据，`ex=ttl_seconds` 自动过期。可以自行扩展：比如把会话标题缓存 5 分钟。

### 3.3 降级设计（重要工程思维）

Redis 挂了怎么办？本项目选择**降级**：限流放行、缓存失效，业务照常跑，只打警告日志。

```python
if not self.available:
    return True, limit   # Redis 不可用 => 放行
```

这样本地没有 Redis 也能开发调试，生产上 Redis 短暂故障也不会拖垮主业务。

### 3.4 缓存三个经典问题（面试常问）

- **穿透**：查一个不存在的数据，每次都打到数据库 → 缓存空值（带短 TTL）
- **击穿**：热点 key 过期瞬间，大量请求同时打 DB → 互斥锁 / 逻辑过期
- **雪崩**：大量 key 同一时间过期 → 过期时间加随机抖动

## 4. 流式输出：SSE 的原理

### 4.1 三种实时方案对比

| 方案 | 方向 | 特点 | 适用 |
|---|---|---|---|
| 轮询 | 客户端反复问 | 简单但浪费、有延迟 | 不推荐 |
| SSE | 服务器单向推 | 基于 HTTP，自动重连，实现简单 | **AI 流式回复、通知推送** |
| WebSocket | 双向全双工 | 复杂，需长连接管理 | 聊天室、游戏、协同编辑 |

本项目选 SSE，因为 AI 回复只需要"服务器往客户端推"。

### 4.2 SSE 长什么样

```
HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache

data: {"type": "start", "session_id": "abc"}\n\n
data: {"type": "token", "content": "你"}\n\n
data: {"type": "token", "content": "好"}\n\n
data: {"type": "done", "message_id": "xyz", "content": "你好"}\n\n
```

每条 `data:` 行以空行结束。客户端逐行接收，收到 token 就渲染 → "打字机"效果。

### 4.3 本项目代码对照（app/routers/chat.py）

```python
async def event_generator():
    yield sse({"type": "start", ...})
    async for chunk in chat_service.stream_reply(...):
        yield sse({"type": "token", "content": chunk})   # 边生成边推
    reply = await chat_service.save_reply(db, session_id, full)  # 完整回复落库
    yield sse({"type": "done", "message_id": reply.id, ...})

return StreamingResponse(event_generator(), media_type="text/event-stream",
                         headers={"X-Accel-Buffering": "no"})
```

**三个容易踩的坑：**

1. **客户端断开**：生成器抛 `asyncio.CancelledError`，要 catch 住把已生成内容保存（本项目已处理，见 `except asyncio.CancelledError`）。
2. **nginx 缓冲**：nginx 默认缓冲响应，导致客户端一次性收到全部内容 → 必须 `proxy_buffering off;` 或响应头 `X-Accel-Buffering: no`。
3. **中间层缓存**：必须 `Cache-Control: no-cache`，否则 CDN/代理会缓存整个流。

## 5. Pydantic 校验：数据进门先验一遍

### 5.1 为什么需要

没有校验：客户端传 `{"content": ""}` 空字符串、`{"age": -1}` 负数、邮箱格式乱写，都会进业务逻辑 → 报错难懂、数据脏。Pydantic 在**入口处**就把关：不合格直接 422，字段错误列表明明白白。

### 5.2 本项目代码对照（app/schemas.py）

```python
class MessageCreate(BaseModel):
    content: str = Field(min_length=1, max_length=4000)  # 非空、不超长

class UserCreate(BaseModel):
    username: str = Field(min_length=3, max_length=50)
    email: EmailStr            # 真校验邮箱格式
    password: str = Field(min_length=6)
```

- `response_model=MessageOut`：保证响应字段白名单（比如永远不泄露 `password_hash`）
- `examples=[...]`：自动生成到 /docs 文档里，别人调用时能看到示例

### 5.3 校验失败长什么样

```json
{
  "code": 42200,
  "message": "请求参数校验失败",
  "detail": [{"loc": ["body","content"], "msg": "String should have at least 1 character", ...}]
}
```

## 6. 统一异常与日志

### 6.1 为什么"统一"

前端拿到错误，不想判断 N 种结构。约定：**所有错误都是 `{code, message, detail}`**。业务代码只管 `raise NotFoundError(...)`，框架统一转 JSON。

### 6.2 错误码设计（app/exceptions.py）

```
4 位 HTTP 状态码 + 2 位业务细分：
40400 资源不存在      40100 密码错误      40101 未登录
40900 已注册          42200 参数校验失败   42900 限流
40001 文件超限        40002 类型不支持     50000 内部错误
```

### 6.3 日志三件套

Python logging：**Logger（记录）→ Handler（输出到哪）→ Formatter（格式）**。

本项目（app/logging_conf.py）：
- 控制台输出（本地看）
- `logs/app.log` 滚动文件（5MB × 3，避免日志无限膨胀）

中间件（app/main.py）为每个请求生成 `X-Request-ID` 并记录耗时：

```
INFO app | POST /chat/sessions/xxx/messages -> 200 45.2ms rid=3f2a9c1b
```

**为什么要 request id**：线上排查时，用户报"我的请求失败了"，凭 request id 就能在日志里把这次请求的所有记录串起来。日志里永远带上它。

## 7. Linux 进程与端口（掌握标准必会）

> 这些命令在本机（Windows 可用 WSL / Git Bash）和服务器上都适用。
> Docker 容器本质也是 Linux 进程，排查思路完全一样。

### 7.1 进程管理

```bash
ps aux | grep uvicorn        # 查看进程（含 PID、CPU、内存）
ps -ef --forest              # 进程树，看父子关系
top / htop                  # 动态监控
kill 1234                   # 温柔终止（发 SIGTERM，进程可清理后退出）
kill -9 1234                # 强制终止（发 SIGKILL，慎用，不清理直接死）
nohup uvicorn app.main:app --port 8000 > app.log 2>&1 &
                            # 后台运行且关终端不退出（& 放后台，nohup 防挂断）
```

### 7.2 端口管理（排"端口冲突"用）

```bash
ss -tlnp | grep 8000        # 谁在监听 8000（-t TCP -l 监听 -n 数字 -p 进程）
netstat -ano | grep 8000    # Windows 等价命令
lsof -i:8000                # 哪个进程占用 8000
fuser -k 8000/tcp           # 杀掉占用 8000 的进程（一条命令搞定）
```

**端口冲突场景**：`uvicorn` 启动报 `Address already in use` → 说明 8000 被占了 → `ss -tlnp | grep 8000` 找到 PID → `kill`。

### 7.3 排查 502 的标准流程

502 的本质：**反代（nginx）连不上上游应用**。所以：

```
1. 应用进程还在吗？        ps aux | grep uvicorn   /   docker compose ps
2. 应用真的在监听吗？      ss -tlnp | grep 8000    （容器里必须监听 0.0.0.0）
3. 应用日志说了什么？      docker compose logs -f api   （崩溃原因在日志里）
4. 反代配置对吗？          upstream 端口、proxy_buffering off、超时时间
5. 是不是 DB/Redis 挂了导致请求处理失败？   curl /healthz 看 db/redis 状态
```

### 7.4 Docker 视角的进程

```bash
docker ps                          # 运行中的容器（相当于 ps aux）
docker compose ps                  # compose 服务状态
docker exec -it week2-api sh      # 进入容器（容器里就是一个精简 Linux）
docker inspect week2-api           # 查看容器配置（端口映射、环境变量、健康检查）
```

## 8. Docker 与 Compose

### 8.1 镜像分层（Dockerfile 为什么这么写）

```dockerfile
COPY requirements.txt .        # 第 1 层：依赖清单
RUN pip install ...            # 第 2 层：装依赖
COPY . .                       # 第 3 层：代码
```

**每一行生成一个只读层，改哪层只重建它之后的层**。所以"先拷依赖清单再拷代码"：代码改动不触发重新下载依赖，构建飞快。反之如果先 `COPY . .` 再装依赖，改一行代码就要重装全部依赖。

### 8.2 容器间通信（compose 的关键）

容器是隔离的，`localhost` 在容器里指容器自己。所以：

- **db 容器**里 PostgreSQL 监听 5432
- **api 容器**要连数据库，必须用服务名：`postgresql+asyncpg://chat:chatpass@db:5432/chatdb`
- 映射 `ports: "8000:8000"` 只是把 api 的 8000 暴露给**宿主机**，容器间通信不走这个

### 8.3 healthcheck + depends_on

```yaml
depends_on:
  db:
    condition: service_healthy   # 等 db 健康检查通过再启动 api
```

没有这个，api 会比 db 先启动 → 连库失败直接崩。这就是"数据库连接失败"最经典的坑之一。

### 8.4 数据卷（持久化的关键）

```yaml
volumes:
  pgdata:/var/lib/postgresql/data   # 容器删了，数据还在卷里
```

`docker compose down` 容器没了数据还在；`down -v` 连卷一起删（**慎用，数据没了**）。

## 9. 接口测试（pytest）

### 9.1 为什么测接口

单元测试测函数，接口测试测"整个 HTTP 链路"：路由 → 校验 → 业务 → 数据库 → 响应格式。改了代码后 `pytest` 一键回归，防止改坏老功能。

### 9.2 本项目测试技巧（tests/conftest.py）

**测试用 SQLite、关掉 Redis** —— 任何机器都能跑，不需要 Docker：

```python
os.environ["DATABASE_URL"] = "sqlite+aiosqlite:///./test_chat.db"
os.environ["REDIS_URL"] = ""
```

**必须在导入 app 之前设置环境变量**，因为 app 在导入时就创建了引擎。

### 9.3 一个测试看什么

```python
def test_08_send_message_and_get_history(client):
    token = register(client, "dave")
    sid = create_session(client, token)
    resp = client.post(f"/chat/sessions/{sid}/messages", json={"content": "你好，FastAPI"}, headers=auth(token))
    assert resp.status_code == 200
    ...
    assert roles == ["user", "assistant"]   # 持久化的证据：历史里有两轮消息
```

测的不仅是"返回 200"，还有**业务行为**（消息落库、角色顺序、自动标题），这才是接口测试的价值。

## 10. 最后：本周知识图谱

```
请求进来
   │
   ▼
中间件（日志 + X-Request-ID）
   │
   ▼
Pydantic 校验 ──不合格──► 422（统一错误格式）
   │ 合格
   ▼
认证（JWT）────未登录──► 401
   │ 通过
   ▼
业务逻辑（services）
   ├── Redis 限流（临时状态，内存，可降级）
   ├── 读历史消息（连接池借连接）
   ├── 流式生成回复（异步生成器 + SSE 推送）
   └── 写消息落库（PostgreSQL 持久化，连接池还连接）
   │
   ▼
统一响应（response_model 白名单）► 客户端
```

**异步**让请求不阻塞，**连接池**让数据库扛住并发，**Redis** 放临时状态，**PostgreSQL** 存持久数据，**SSE** 做流式输出，**统一异常+日志**让线上可排查，**Docker Compose** 让整个环境一键复现 —— 这就是本周交付的全部知识点。
